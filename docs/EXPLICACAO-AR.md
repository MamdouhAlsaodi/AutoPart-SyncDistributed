# شرح مشروع AutoPart-SyncDistributed بالعربية

> دليل لفهم المشروع وتحضير عرضه. [العرض البرتغالي التفاعلي](apresentacao.html) و[نسخته PDF للاستخدام دون خادم](apresentacao.pdf) هما مادة التقديم، و[نص الإلقاء المرافق](presentation-script.ar-pt.md) يتبع ترتيب شرائحه. أما [وثيقة البنية البرتغالية](FRAMEWORK.md) و[التقرير](../RELATORIO_PROJETO.md) ففيهما التفصيل الأكاديمي.

## الفكرة والنطاق

AutoPart-SyncDistributed نموذج أولي أكاديمي لمتجر قطع غيار سيارات، موجّه لشرح تدفّق من الكتالوج إلى الطلب وإدارة المخزون في مادة **Negócios Eletrônicos**. يستطيع الزائر البحث في القطع وعرض تفاصيلها؛ يضيف العميل القطع إلى سلته، يسجل الدخول ويرسل طلبًا؛ ويدير المشرف القطع والمخزون وحالات الطلبات. تسجيل الطلب **محاكاة للبيع**: يُحفظ طلب في قاعدة البيانات ويُخفَّض المخزون وفق قواعد الخادم، لكن لا توجد عملية دفع أو فاتورة أو شحن أو بيع حقيقي.

## كيف تُوزّع المسؤوليات؟

```text
متصفح العميل: HTML / CSS / JavaScript، وسلة محفوظة في localStorage
      │ طلبات HTTP / JSON عبر fetch
      ▼
خادم Node.js / Express 5: مسارات API، تحقق، صلاحيات، أسعار ومخزون
      │ Mongoose
      ▼
MongoDB محلي: مستخدمون وقطع وطلبات وبيانات أخرى
```

- **الواجهة** داخل `client/`؛ تعرض البيانات وتتواصل مع API عبر `client/js/api.js`. حفظ السلة في المتصفح لا يجعل السعر أو المخزون المرسَل منه مصدرًا موثوقًا.
- **الخادم** يبدأ من `server/index.js`، ويجمع المسارات وتقديم الموقع والعرض في `server/src/app.js`. قواعد التعامل مع الطلبات موجودة في `server/src/controllers/OrdersController.js`، وصلاحيات الوصول في `server/src/middleware/auth.js` ومسارات `server/src/routes/`.
- **قاعدة البيانات** MongoDB عبر Mongoose. تهيئة `compose.yaml` المحلية تستخدم replica set **بعضو واحد** حتى تعمل المعاملات؛ هذا ليس تكرارًا موزعًا بين خوادم ولا يثبت التوافر العالي.

اسم المشروع يحوي «Distributed»، لكن الموجود حاليًا **فصل منطقي بين المتصفح وAPI وقاعدة البيانات**: Express يقدم الواجهة والـAPI من عملية خادم واحدة، وMongoDB خدمة محلية منفصلة. لا ندّعي نشر النظام على عدة عقد، أو موازنة أحمال، أو تحمل أعطال الإنتاج. كذلك التقنية الحالية **Node.js/Express/MongoDB** وليست PHP/Slim/SQL Server المذكورة في النسخة التاريخية من التقرير القديم.

## رحلة طلب واحدة

1. يفتح المستخدم الكتالوج العام عبر `GET /api/catalogo` ويبحث عن القطعة المناسبة.
2. يحتفظ المتصفح بعناصر السلة في `localStorage`؛ لا تُعامل أسعار السلة على أنها مصدر الحقيقة.
3. بعد الدخول، يرسل العميل القطع والكميات إلى `POST /api/orders/checkout`.
4. يجلب الخادم المنتجات والأسعار والمخزون، ويتأكد من توفر الكمية. إنشاء الطلب وتخفيض المخزون يتمان ضمن **معاملة MongoDB** في التنفيذ الحالي؛ إذا فشلت العملية لا ينبغي عرضها كشراء ناجح.
5. يعرض العميل طلباته من `GET /api/orders/me`؛ ومسارات `/api/admin` مخصصة للإدارة وتتحقق من الدور في الخادم، لا بمجرد إخفاء زر في الواجهة.

> المثال التعليمي: إذا عُدِّل السعر في أدوات المتصفح، لا يُعتمد الرقم عند تأكيد الطلب؛ الخادم يعيد الحساب من بيانات القطعة المخزنة لديه.

## المصادقة وحدود الأمان

التسجيل والدخول يتمان عبر `/api/auth`، وكلمات المرور تحفظ كتجزئة باستخدام `bcryptjs`. يستخدم النظام JWT موقّعًا بمفتاح `JWT_SECRET` يُضبط محليًا ولا يُنشر. للمشرف والعميل صلاحيات مختلفة؛ رفض العميل من مسار إداري بحالة 403 دليل محدود على تطبيق قاعدة الصلاحيات في ذلك الفحص، وليس شهادة شاملة بأمان الإنتاج. لا تضع مفتاح JWT أو بيانات حقيقية في الشرائح أو المستودع.

## الأدلة التي يجوز ذكرها

تسجل [مراجعة الجاهزية المؤرخة 16-09-2026](READINESS-ASSESSMENT-2026-09-16.md) **22 اختبارًا ناجحًا دون فشل** في تلك الجولة، مع فحوص تشغيل محلية للكتالوج والدخول ومسارات الطلب والإدارة، ورفض وصول عميل إلى مسار إداري (403). هذه نتائج **بتاريخها**، وليست ضمانًا بأن البيئة الحالية تعمل الآن؛ أعد تشغيل الاختبارات والتحقق قبل التقديم. هناك صور محلية حقيقية للمتجر والإدارة والعرض ضمن `docs/screenshots/`، لكنها لا تغطي بصريًا كل تدفق على حدة. لا توجد حزمة Playwright E2E موثقة، ولا نشر عام للتطبيق.

## التحضير لعرض حي

اتبع [README](../README.md) لتثبيت الاعتمادات وتشغيل MongoDB والخادم. المنفذ الافتراضي هو **3000**؛ إذا ضبطت `PORT=5500` فاستخدم 5500 في كل الروابط. قبل العرض جهز `.env` محليًا بمفتاح `JWT_SECRET` خاص، وإن أردت الحسابين التجريبيين فعّل `SEED_DEMO_DATA=true` وحدد `SEED_DEMO_PASSWORD` محليًا. لا تفترض وجود حسابات تجريبية ما لم تنفذ إعدادها. افتح `/apresentacao` للشرائح، وجرّب الكتالوج وعميلًا ومشرفًا وحالة 403 قبل الحضور. أبقِ بيانات العرض التجريبية منفصلة عن قاعدة الاختبارات التي قد تُمسح أثناء الاختبار.

## أجوبة قصيرة للأسئلة المتوقعة

- **لماذا Express؟** لتنظيم طلبات HTTP ومسارات REST والوسائط (middleware)، مع بقاء منطق الطلب والتحقق في الخادم. هذا وصف للتطبيق الحالي، لا ادعاء أننا أنشأنا إطارًا جديدًا.
- **أين التوزيع؟** بين متصفح يستهلك API وخادم يعالج وقاعدة بيانات محلية؛ ليس هناك عدة خوادم أو high availability.
- **هل يمكن استخدامه تجاريًا؟** ليس بعد: الدفع والشحن والتشغيل العام غير منفذة، والتقييم الأمني/الخصوصية للإنتاج خارج نطاق النموذج.
- **ما الذي يميّز الطلب عن مجرد واجهة؟** الطلب وسعره ومخزونه يُتحقَّق منها في الخادم ويُحفظ في قاعدة البيانات، بدل الاعتماد على سلة المتصفح وحدها.
